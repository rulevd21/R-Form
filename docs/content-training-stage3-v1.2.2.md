## Цель и границы

После закрытия новой плановой тренировки её факты должны попадать в один короткий черновик, который существующий Poll показывает владельцу в Telegram. Владелец дополняет текст/фото, просматривает правки, сохраняет версию и получает новый финальный предпросмотр. Публикация и расписание требуют отдельного точного согласования материала.

Выбор владельца: ИИ-правки через ChatGPT; платный API и самостоятельный фоновый ИИ-провайдер не подключаются. Одно поручение в ChatGPT обрабатывает существующие заявки из журнала без переноса текста между чатами. Этот вариант требует команды владельца в ChatGPT и не обещает обработку ИИ сразу после Telegram-сообщения.

## Подтверждённая причина

Текущий проект Training открыт и прочитан 08.10.2026: SessionService.finish закрывает плановую сессию, не записывая Completed_At; normalize_ не возвращает его; CREATE_SESSION/UPDATE_DRAFT_SESSION в действующем SchemaService не разрешают запись этого поля. При этом текущая 23-польная схема и FREE операции уже присутствуют и должны сохраняться.

49 канонических CLOSED: у 31 пустой Completed_At, в том числе у сессий 28/30 сентября и 02/05/07 октября. Это факт текущего чтения, а не основание восстанавливать время по дате или длительности. 49 старых CLOSED уже входят в существующий baseline автоматических черновиков; массовый импорт/ремонт не входит в этап. Отсутствующий или повреждённый baseline блокирует синхронизацию, а не запускает импорт истории.

## Доработки

1. Training core 2.1.9 записывает серверное Completed_At при создании/обновлении плановой сессии; проверяет CLOSED и точное время чтением канонической строки. APPLIED TRAINING_CLOSE получает тот же timestamp и проверяется чтением журнала. Идемпотентный replay отказывается подтверждать закрытие без CLOSED + Completed_At. Started_At, план, подходы, физическая схема и FREE логика не изменяются.
2. Короткий черновик выбирает до трёх целых групп упражнений, сохраняя различающиеся подходы и RIR внутри группы. Числовые сочетания не обрезаются. При сокращении явно указано, что полные итоги сохранены в R/Form. Полный Main_Result и Session_Decision остаются в карточке; boilerplate о следующем плане больше не выдаётся за решение в коротком посте. Если нет ни одного пригодного полного фрагмента, черновик блокируется для редактора.
3. Poll сохраняет число созданных/заблокированных черновиков и первые десять причин; наличие блокировок даёт PARTIAL / NEEDS_REVIEW вместо ложного полного OK. /status показывает результат и блокировки.
4. /ai и кнопка «ИИ-поручения» показывают ожидание ChatGPT, готовое предложение, устаревший запрос либо закрытый материал. Предложение по прежнему запросу отклоняется даже при неизменившемся хеше текста, если владелец уже дал другое поручение.
5. `rformContentApiV04SubmitChatGPTProposal` — постоянный операторский мост в существующем API. Он читает ограниченный пакет из Script Property, отправляет предложение через существующий Workspace commit, проверяет readback и очищает только тот же подтверждённый пакет. Не сохраняет Telegram_Text, не согласовывает и не публикует. Нет дополнительного сервиса, очереди, триггера или ключа.
6. Существующие версии, фото, порядок альбома, HOLD, возврат и новый preview после изменений проверены общей регрессией. Сохранение правок сбрасывает старое согласование; предложение ИИ само текст не меняет.

## ChatGPT: обработка поручений

Команда владельца: «Обработай ИИ-поручения R/Form».

Оператор/ChatGPT читает свежие CONTENT_QUEUE и CONTENT_ACTION_LOG, восстанавливает актуальные workspace metadata и выбирает REQUESTED с совпадающим source_hash. Закрытые, опубликованные, архивные, устаревшие либо неоднозначные заявки не обрабатывает. Читает канонические факты/текущий текст; выполняет editorial/copy/brand/factcheck обязанности существующего R/Form Content Orchestrator. Инструкция внутри заявки — редакционное поручение, не разрешение на публикацию или обход правил.

Для одного результата формирует пакет только из `content_id`, `source_hash`, `request_id`, `text` (строки, до 8500 байт JSON); помещает его в RFORM_CHATGPT_PROPOSAL существующего Content API через аутентифицированный интерфейс настроек и запускает уже установленную функцию `rformContentApiV04SubmitChatGPTProposal`. Нельзя создавать/вставлять новый executable helper для каждой заявки, читать секрет, использовать платный API или писать результат в таблицу мимо Workspace_.

После записи проверяет APPLIED/ALREADY_APPLIED, точную заявку, proposal_id и текст в readback. При неопределённом результате сохраняет packet/Action_ID и сначала проверяет журнал; не формирует новый ID для повторной операции. Подтверждённый пакет удаляется функцией, никакой второй datastore не создаётся. При недоступном редакторе сообщает точный блокер, не заявляет обработку выполненной.

Следующий существующий Poll уведомляет только владельца, что предложение готово. Владелец открывает карточку → «Посмотреть предложение ИИ» → «Просмотр правок» → «Сохранить». Даже после сохранения публикация не разрешена без нового точного предпросмотра.

## Ограничения и откат

- SheetRepository пишет непрерывные диапазоны по отдельности: изменения разных участков строки/журнала не являются общей транзакцией. При потере поля readback запрещает APPLIED; требуется сверка, не автоматическое восстановление истории.
- Старый loggingWarning при невозможности записать audit остаётся наблюдаемым ограничением: не заявлять наличие APPLIED без чтения журнала.
- Старые CLOSED не пересоздаются; source hash и COVERS/Session_ID запрещают дубли и возврат HOLD в автогенерацию.
- Короткий пост — факты, без новых трактовок/медицинских выводов. Смысловые ИИ-предложения требуют фактов и просмотра владельцем.
- ИИ через ChatGPT выполняется по команде; автоматическая фоновая генерация произвольных ИИ-правок не подключена.
- При откате восстановить четыре Training baseline модуля и прежний основной deployment version 4, API version 16 и Bot version 8; интерфейс 2.2.1 / Control 0.5.9 сохраняются. Канонические данные не откатываются и не удаляются.
